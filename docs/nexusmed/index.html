API DE INTEGRAÇÃO — HMAC-SHA256

Nexus Med API Documentação

Integre o laboratório, o sistema de recepção/PMS ou o ERP da clínica ao Nexus Med. Duas direções de integração: inbound (dado entra no Nexus Med, autenticado por assinatura HMAC-SHA256) e outbound (o Nexus Med envia documentos assinados/finalizados para o sistema do médico, ainda em Beta).

1. Visão Geral

A API do Nexus Med conecta o prontuário eletrônico a sistemas externos de saúde — laboratórios, sistemas de recepção/PMS e ERPs — por três fluxos distintos, cada um com seu próprio contrato de dados.

Fluxos Disponíveis

  • Inbound — Exames e Laudos: um laboratório envia o resultado de um exame (JSON estruturado) ou o arquivo de um laudo (PDF/imagem) para vínculo automático com o paciente do médico.
  • Inbound — Pacientes: o sistema de recepção/PMS externo da clínica sincroniza cadastro e atualização de pacientes.
  • Outbound — Documentos BETA: quando um documento se torna imutável (assinado ou finalizado), o Nexus Med envia automaticamente uma notificação para o webhook_url configurado pelo médico.

Sem OAuth2, sem JWT

Toda integração de sistema externo (laboratório, PMS, ERP) autentica por assinatura HMAC-SHA256 — não há login de usuário nem token OAuth para essas rotas. JWT é usado apenas quando o próprio médico está autenticado dentro do Nexus Med.

2. Ambiente e Base URL

O ambiente de produção está acessível através da seguinte URL base:

https://ia-comunica-core-api.vercel.app

Cada rota do Nexus Med tem um endpoint de teste de conectividade, sem autenticação, útil para validar que a integração enxerga o serviço antes de configurar HMAC:

Health checkFluxo
GET /nexus/inbound-exam/healthInbound — exames
GET /nexus/laudos-inbound/healthInbound — laudos/arquivos
GET /nexus/inbound-patient/healthInbound — pacientes

Observação: não existe hoje um domínio customizado para esta API (ex.: nexusmed.iacomunica.com.br) — a URL base é o domínio raiz da Vercel do projeto. HTTPS é obrigatório em todas as requisições.

3. Autenticação — HMAC-SHA256 v2 (Inbound)

As três rotas inbound (exames, laudos/arquivos e pacientes) compartilham o mesmo mecanismo de autenticação: uma credencial por médico/sistema externo, assinando cada requisição com HMAC-SHA256.

Headers Obrigatórios

Header Descrição
x-nexus-tenant Identifica o médico/tenant destinatário — o doctor_id (UUID) ou, em algumas rotas, um alias alfanumérico previamente cadastrado.
x-nexus-external-system Identificador do sistema externo (o mesmo usado no cadastro da credencial), ex.: fleury, dasa.
x-nexus-timestamp Unix timestamp em segundos do momento do envio. Janela de aceitação: ±120 segundos.
x-nexus-signature Assinatura HMAC-SHA256, formato sha256=<hex>.
x-nexus-delivery-id Identificador único desta entrega, definido pelo sistema externo — chave de idempotência (ver seção 8).
Content-Type Deve ser exatamente application/json — sem isso o corpo bruto usado na verificação de assinatura não é capturado, e a requisição é rejeitada.

Cálculo da Assinatura

A assinatura é calculada sobre um canonical de 8 linhas, separadas por \n (sem quebra final), sem nenhuma normalização de campo:

canonical
NEXUS-HMAC-V2
<METODO HTTP EM MAIUSCULO>
<PATH + QUERY EXATOS DA REQUISICAO>
<x-nexus-timestamp>
<x-nexus-tenant>
<x-nexus-external-system>
<x-nexus-delivery-id (ou vazio, se a rota nao exigir)>
<SHA256_HEX(corpo exato da requisicao)>

NEXUS-HMAC-V2 é um separador de domínio criptográfico fixo, sempre exatamente esse texto — garante que esta assinatura nunca colide com outro uso de HMAC-SHA256 no ecossistema. O resultado final vira o header:

x-nexus-signature: sha256=<hmac_sha256_hex(secret, canonical)>

Assine exatamente os bytes transmitidos

Se sua biblioteca HTTP reformatar o corpo depois de assinado (reordenar chaves, mudar indentação) ou normalizar a URL, o hash não bate mais. Assine os bytes exatos, na ordem exata em que serão transmitidos — inclusive path e query string.

4. Como Obter a Credencial SELF-SERVICE

O provisionamento da credencial HMAC é feito pelo próprio médico, dentro do Nexus Med — sem depender de um processo manual com o time da IA Comunica.

1
O médico gera a credencial

Dentro do Nexus Med: Configurações → Integrações → "Credenciais de integração".

2
Link de resgate de uso único

O médico recebe um link válido por 72 horas — ele mesmo nunca vê o valor da chave.

3
Envio ao contato técnico

O médico envia o link para o contato técnico do laboratório ou do sistema parceiro.

4
Resgate de uso único

O parceiro abre o link, a chave é revelada exatamente uma vez, e deve ser guardada com segurança a partir daí.

5
Sem processo manual

Nenhuma etapa depende do time da IA Comunica — o fluxo inteiro acontece dentro do produto.

Se o link expirar ou a chave se perder, não há como recuperar o valor — o médico precisa gerar uma nova credencial (rotação), o que invalida a anterior dentro de uma janela de transição.

5. Inbound — Exames e Laudos

Um laboratório ou sistema externo envia o resultado de um exame de duas formas: um resultado estruturado (JSON) ou o arquivo de um laudo (PDF/imagem). Os dois caminhos usam a mesma autenticação HMAC da seção 3.

5.1 — Resultado estruturado

POST /nexus/inbound-exam

Não há schema JSON rígido — o corpo é armazenado criptografado e processado depois, de forma assíncrona. Estrutura recomendada:

json
{
  "delivery_id": "LAB-EXAMPLE-000123",
  "external_system": "lab-exemplo",
  "exam_type": "HEMOGRAMA",
  "external_patient_id": "PAC-000123",
  "exam_date": "2026-08-20",
  "requesting_physician": "Dr. Fulano de Tal",
  "notes": "Observações clínicas relevantes, se houver",
  "results": {
    "hemoglobina": "14.5 g/dL",
    "hematocrito": "43%"
  }
}
Vínculo com o paciente:

Sempre envie external_patient_id com um identificador estável do paciente. Sem ele, o exame cai em uma fila de pendências para vínculo manual do médico.

Status de uma entrega específica: GET /nexus/inbound-exam/:deliveryId/status (mesma autenticação HMAC, com o path assinado).

5.2 — Arquivo de laudo (fluxo em 2 chamadas)

Quando o que o laboratório tem é um arquivo (PDF, imagem), o envio acontece em duas etapas — o arquivo nunca trafega pela core-api, só a autorização de upload:

1
POST/nexus/laudos-inbound/upload-url

Autenticado por HMAC. Devolve uma signed URL de upload direto no Storage, referenciada por um upload_ticket_id.

2
PUT direto no Storage

O laboratório envia os bytes reais usando a upload_url/token recebidos — fora da core-api.

3
POST/nexus/laudos-inbound/webhook

Notifica o Nexus Med do laudo recebido, referenciando o upload_ticket_id da etapa 1. Mesma autenticação HMAC.

Campos aceitos no webhook (além de upload_ticket_id): lab_id, laudo_tipo, laudo_data, laudo_referencia (chave de idempotência do lado do laboratório), tipo_envio (laudo_pronto ou exame_bruto), além de campos opcionais de identificação do paciente (paciente_cpf_hash, paciente_nome, paciente_data_nascimento) e metadados do arquivo (arquivo_mime_type, arquivo_tamanho, arquivo_nome).

Limites técnicos: corpo máximo de 256 KB em /nexus/inbound-exam. Rate limit de 60 req/min por par (tenant, sistema externo) em /nexus/inbound-exam, e 100 req/min em /nexus/laudos-inbound/*.

6. Inbound — Pacientes

Sincronização de cadastro/atualização de paciente vinda do sistema de recepção/PMS externo da clínica — mesmo substrato de credencial HMAC das seções 3 e 5 (o mesmo secret cadastrado pelo médico serve para exames e para pacientes).

POST /nexus/inbound-patient

Também sem schema rígido. Campos reconhecidos no corpo:

CampoDescrição
external_patient_idIdentificador do paciente no sistema externo (aceita também patient_id/paciente_id por tolerância). Usado primeiro na tentativa de vínculo.
cpfUsado como critério de vínculo/criação quando o checksum é válido.
full_nameObrigatório na prática para criação automática de um novo paciente.
birth_date, gender, phone, email, address, cnsCampos administrativos complementares.
clinic_external_refReferência da clínica no sistema externo — ajuda a resolver a clínica automaticamente quando o médico atende em mais de uma.

Quando o vínculo automático não é possível (sem external_patient_id conhecido e sem CPF válido, por exemplo), o evento entra em uma fila de revisão para o médico resolver manualmente dentro do Nexus Med.

Status de uma entrega específica: GET /nexus/inbound-patient/:deliveryId/status. Rate limit: 60 req/min por par (tenant, sistema externo).

7. Outbound — Envio de Documentos BETA

Este fluxo está em Beta. A engenharia está pronta e ativa, mas ainda não foi validada de ponta a ponta com um destinatário real em produção. Trate como preview técnico, não como contrato estável para uso imediato.

Quando um documento do Nexus Med se torna imutável — assinado (ICP-Brasil) ou finalizado, dependendo da preferência de assinatura configurada na integração — o Nexus Med envia automaticamente um POST para o webhook_url que o médico configurou dentro do produto.

Envelope enviado

O envelope nunca inclui dado clínico bruto — nome de paciente, CPF, CID ou conteúdo do documento. Só metadados e uma signed URL de download de curta duração:

json
{
  "event_id": "01hxxxxxxxxxxxxxxxxxxxxxxx",
  "source": "nexus-med",
  "type": "laudo.assinado",
  "occurred_at": "2026-08-29T14:32:10.000Z",
  "tenant_id": "doctor-uuid-real-do-medico",
  "payload": {
    "entity_type": "laudo",
    "entity_id": "uuid-do-laudo",
    "patient_external_id": "PAC-000123",
    "document_type": "laudo_hemograma",
    "signature_status": "signed_by_nexus",
    "signature_method": "icp_brasil",
    "finalized_at": "2026-08-29T14:32:05.000Z",
    "signed_at": "2026-08-29T14:32:08.000Z",
    "document_sha256": "<sha256 hex do arquivo>",
    "download_url": "<signed URL, TTL curto>",
    "download_expires_at": "2026-08-29T14:47:08.000Z"
  }
}

patient_external_id só é preenchido quando o paciente já está mapeado para um identificador externo — caso contrário, é null. signed_at/signature_method só são preenchidos quando signature_status = "signed_by_nexus".

Autenticação — NEXUS-OUTBOUND-HMAC-V1

Esquema diferente da inbound (nomes de header e canonical distintos — não reaproveite código):

HeaderDescrição
x-nexus-event-iduuid-v7 do evento — o mesmo event_id do envelope.
x-nexus-timestampUnix timestamp em segundos, no momento do envio.
x-nexus-signatureHMAC-SHA256, formato sha256=<hex>, calculada sobre o canonical de 4 linhas abaixo.
canonical
NEXUS-OUTBOUND-HMAC-V1
<x-nexus-event-id>
<x-nexus-timestamp>
<SHA256_HEX(corpo exato do envelope)>

Retentativas

Até 5 tentativas de entrega, com backoff exponencial e jitter (~1min, 5min, 25min, 2h). Classificação da resposta do seu servidor:

RespostaClassificação
2xxEntregue — não retenta.
429 / 5xx / timeoutRetentável — nova tentativa com backoff.
4xx (exceto 429)Falha terminal — nunca retenta.

Requisitos de segurança do envio: apenas HTTPS, sem seguir redirecionamento, timeout de 10s, corpo de resposta do seu servidor truncado antes de qualquer log. O webhook_url é configurado pelo médico dentro do Nexus Med, na própria integração.

8. Respostas HTTP e Idempotência

Código Quando ocorre O que fazer
202 Entrega nova, aceita e enfileirada. Sucesso — nada a fazer.
200 Reenvio de um delivery_id já processado (idempotência) ou resposta de /health. Sucesso — tratar como confirmação, não reenviar de novo.
400 Header x-nexus-delivery-id ausente, ou corpo não é JSON válido. Corrigir a requisição — não é erro transitório.
401 Header de autenticação ausente, timestamp fora da janela, assinatura não confere, ou nenhum secret cadastrado para o par tenant+sistema. Verificar headers, timestamp e secret — não adianta reenviar sem corrigir a causa.
429 Limite de requisições por minuto excedido. Reduzir a taxa de envio, aplicar backoff.
5xx Falha interna do servidor. Retentar com backoff exponencial — seguro reenviar com o mesmo delivery_id.

Idempotência

delivery_id é definido por quem envia (nunca pelo Nexus Med). A chave de unicidade real é o trio (tenant, external_system, delivery_id) — reenviar o mesmo delivery_id dentro desse par nunca processa duas vezes, e devolve o registro já persistido.

Nunca reutilize um delivery_id para um evento diferente. Só o identificador é comparado, não o corpo — reusar o mesmo id com um corpo diferente descarta o novo conteúdo silenciosamente, mantendo o da primeira tentativa.

9. Logs e Auditoria

Por política de LGPD (Art. 46), o log de cada entrega nunca contém o conteúdo do exame/laudo nem dado clínico de paciente. Os campos registrados por entrega:

delivery_id / external_system
http_status / latency_ms
payload_size_bytes

Em caso de falha de autenticação, o valor cru do x-nexus-tenant recebido nunca é registrado — só o desfecho e o external_system.

10. Boas Práticas

1
Proteja o secret

Nunca exponha a credencial HMAC em código client-side, repositórios públicos ou logs. Ela nunca é enviada em texto claro pela IA Comunica — só pelo link de resgate de uso único.

2
Assine os bytes exatos

Path, query e corpo entram na assinatura exatamente como serão transmitidos — sem reformatar o JSON nem normalizar a URL depois de calcular o hash.

3
Retentativas com critério

Retente com backoff em 429 e 5xx/timeout. Nunca retente 400/401 sem corrigir a causa primeiro — vai gerar o mesmo erro de novo.

4
Identificadores estáveis

Use external_patient_id/delivery_id de forma consistente — evita vínculo manual desnecessário e duplicação de registros.

11. Versionamento

O contrato inbound está na sua 2ª versão do canonical HMAC (v2): a assinatura passou a vincular também o método HTTP, o path/query exatos e o delivery_id, fechando uma brecha onde uma assinatura válida podia ser reaproveitada trocando só o identificador de entrega. Foi uma mudança sem caminho de compatibilidade com a v1 — não havia integração real em produção no momento da migração.

O contrato outbound está na sua 1ª versão (NEXUS-OUTBOUND-HMAC-V1) e permanece em Beta (ver seção 7) até a primeira validação de ponta a ponta com um destinatário real.
